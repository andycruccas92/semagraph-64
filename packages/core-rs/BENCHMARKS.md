# Benchmarks

Throughput benchmarks for the classification kernel live in
`benches/throughput.rs` and run under [Criterion](https://crates.io/crates/criterion).

## What is measured

The benchmark exercises four paths over deterministically generated data:

| group / bench | path under test | reported metric |
|---|---|---|
| `transition_classification/naive_per_item` | `lookup_transition64` + `pack_transition64`, one call per item | transitions/sec |
| `transition_classification/branchless_table` | `classify_branchless_packed`, one call per item | transitions/sec |
| `transition_classification/batch` | `classify_batch` over struct-of-arrays input | transitions/sec |
| `transition_classification/batch_simd` (only with `--features simd`) | `classify_batch_simd` (x86_64 SSE2) | transitions/sec |
| `trajectory_compression/compress_batch_per_trajectory` | `compress_trajectory_batch` over a 10k-trajectory ensemble | trajectories/sec |
| `trajectory_compression/compress_batch_per_transition` | same call, counted per step | transitions/sec |

## Reproducibility

All data is generated by a SplitMix64 PRNG with fixed, recorded seeds — there is
no clock- or address-derived randomness, so a given machine reproduces the same
inputs every run.

- Base seed: `0x9E37_79B9_7F4A_7C15` (transition pairs).
- Ensemble seed: base seed XOR `0xD1B5_4A32_D192_ED03`.
- Transition workload: `65_536` random `(source, target)` pairs over `0..63`.
- Trajectory workload: `10_000` trajectories, each of random length `8..=256`
  over the Q3 alphabet `0..7`.

## How to run

```bash
cd packages/core-rs
cargo bench                 # scalar paths
cargo bench --features simd # adds the SSE2 batch bench on x86_64
```

Criterion writes detailed reports (including throughput in elements/sec) to
`target/criterion/`.

## Architectural expectations (not measurements)

The following are design expectations to confirm against the numbers above, not
results. They are stated so a reviewer knows what "good" looks like:

- The branchless table path should be at least as fast as the naive path, because
  it replaces a chain of comparisons with constant-time table loads from a working
  set that fits in L1 (see `src/tables.rs`, ~4.4 KiB of tables).
- The batch path should meet or exceed the per-item branchless path, because its
  flat struct-of-arrays loop is the shape the autovectorizer can widen.
- The SIMD batch path may improve on the scalar batch for the XOR/mask portion;
  the gain is bounded by the table gather, which is scalar on SSE2. It exists to
  demonstrate the layout, not to claim a specific speedup.
- All four paths produce identical output; this is asserted by tests, not assumed.
